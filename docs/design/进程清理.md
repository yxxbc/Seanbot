# 常驻会话的进程清理

> 使用层面的说明见内置知识库条目 `kb/AboutSeanbot/02-ProcessCleanup.md`（随二进制分发、可由 `sean kb update` 同步）；
> 本文是它的**实现细节版**：保留代码位置与手工复现实验步骤，随仓库发布在 `docs/design/`。

`bash` 工具带 `session` 参数时会在后台留一个常驻 shell（`bash -s`）；会话里可能起后台任务，甚至 `setsid` 出来的守护进程。
只要 Seanbot 退出，这些进程必须一个不剩——验收脚本按 pid 与进程标记双重扫描 `ps`，任何残留都判失败。

难点不在「杀」，而在**退出路径太多、能动手的时刻太少**，加上几个反直觉的平台行为。下面这些坑都实测过。

## 踩过的坑

| 现象 | 原因 |
| --- | --- |
| `Drop` 没执行 | `std::process::exit()` 跳过所有析构（panic=abort、被 SIGKILL 同理） |
| 指望子 shell 读到 stdin EOF 自杀 → 后台任务照旧残留 | POSIX 规定非交互 shell 里的异步列表（`cmd &`）**先把 stdin 接到 `/dev/null`**：后台作业根本不吃 EOF。EOF 只让会话 shell 自己退出，它 fork 出来的作业会变成孤儿 |
| 在 macOS 上按环境变量标记扫进程找不到 | 内核只允许读**自己**进程的环境（`KERN_PROCARGS2` 只对调用者返回，`ps eww` 与 brew 里的进程工具走的都是同一套系统调用）；Linux 能读 `/proc/<pid>/environ` |
| `setsid` 逃逸的进程收不到 | 它不在会话的进程组里，`killpg` 打不到；但它**没改 ppid**，按 ppid 树能找到 |
| 顺序错了就再也找不回 | 一旦先 `killpg`，逃逸进程被 reparent 到 init（pid 1），ppid 树就断链了 |

## 六层保证

| 层 | 覆盖的退出方式 | 机制 |
| --- | --- | --- |
| 1 显式 `shutdown()` | CLI 每条退出路径、工具 `bash_session close_all` | 逐个 `Session::shutdown()` |
| 2 `Drop` | 正常返回、错误返回、panic 展开 | `BashSessions` 的最后一个持有者收尾 |
| 3 **进程级退出钩子** | `std::process::exit()`（跳过 Drop） | 会话登记 `(进程组 pid, 会话标记)`，`libc::atexit` 钩子里按第 1 层同样的顺序收尾 |
| 4 **会话 shell 看门狗** | 父进程被 SIGKILL（连钩子都跑不到） | `__sb_parent=$PPID`；后台子 shell 盯着父进程与 `$$`，谁没了就 `kill -KILL 0` |
| 5 `EXIT` 陷阱 + EOF 兜底 | shell 自己退出时顺手清一遍 | `trap '__sb_kill_descendants; __sb_kill_escaped; kill 0; exit 0' EXIT` |
| 6 进程组 + ppid 树 / 标记扫描 | 关闭、超时、取消 | `process_group(0)` 独占进程组 → `killpg(SIGKILL)`；逃逸进程按 ppid 树收，Linux 再按标记扫 `/proc` 补一遍 |

收尾顺序固定为 **ppid 树 → `killpg` → 标记扫描**：反过来逃逸进程会被 reparent，找不回来了。

### 第 3 层：进程级退出钩子（`exit_guard`）

- `Session::spawn` 成功后登记，`Session::shutdown` 里注销。注销不只是省一次 kill，更是避免 **pid 被复用**后钩子误伤无关进程。
- 钩子用 `ACTIVE.try_lock()`：退出期间别的线程可能正持着锁，钩子绝不能阻塞，拿不到锁就交给各自的 Drop。
- `std::process::exit()` 会跑 `atexit`（CRT 语义），所以「程序自己退出」的每条路都是进程自己在收尾，不靠子 shell 自觉。

### 第 4 层：看门狗

```bash
__sb_parent=$PPID   # 会话 shell 的父进程就是 Seanbot
( while kill -0 "$$" 2>/dev/null && kill -0 "$__sb_parent" 2>/dev/null; do sleep 1; done; kill -KILL 0 ) >/dev/null 2>&1 &
```

- 子 shell 里的 `$$` 仍是会话 shell 的 pid（bash 语义），于是一个循环同时盯着「会话 shell 还在不在」与「Seanbot 还在不在」。
- 用 `SIGKILL` 而不是 `SIGTERM`：不可被忽略，也不给逃逸留窗口；`kill 0` 只打自己所在的进程组（每会话独占），连看门狗自己一起端掉，收尾不需要善后。

## 怎么验证

```bash
bash scripts/tests/bash_session_test.sh   # 六个场景：drop / exit / closeall / escape+drop / escape+exit / timeout
scripts/test.sh                           # 全套：格式 / clippy / 测试 / 脚本测试
```

改动这层代码时，除了上面两条，值得手工复现两个关键时刻：

1. **退出钩子确实在跑**：造一个假 `ps` 放在 `PATH` 最前面（记录 `$PPID` 后 `exec` 真 `ps`），让探针走 `exit` 出口——日志里会出现父进程 = 正在退出的那个进程的调用（ppid 树与标记扫描各一遍）。
2. **看门狗确实在盯**：起一个会话并一直握着它的 stdin 管道（EOF 永远不来），再把「父进程」`kill -9`——1 秒内整组消失，`ps` 扫不到任何带标记的进程。

## 扩展时注意

- 新增与会话有关的代码路径时别绕过 `Session::spawn` / `Session::shutdown`：登记与注销是配对的。
- Windows 有 Git Bash 时走同一套 POSIX 逻辑；没有时用 PowerShell 会话，清理靠 `taskkill /T`（无标记扫描，看门狗是 POSIX 专属），Windows CI 跳过 shell 脚本测试。
- 若某个平台退出时不跑 `atexit`，第 1、2、4、5、6 层仍然接着。
