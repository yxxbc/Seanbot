# 代码审查清单

## 何时用

用户要求"看看这段改动 / review 一下 / 这个 PR 有没有问题"，或者你刚改完一处较大的变更、
准备在汇报前自己过一遍时。

## 步骤

1. **先确定范围**：用 \`bash\` 跑 \`git diff --stat\` 与 \`git status\`，列出改了哪些文件；
   范围不清就先问用户，别对没看到的改动下结论。
2. **逐文件读改动**：用 \`git diff <文件>\` 看具体改动，必要时 \`read\` 上下文——
   只看 diff 容易漏掉"这个函数在别处怎么被调用"。
3. **过一遍检查项**：
   - 正确性：边界条件（空、0、超大）、错误路径、返回值有没有被忽略
   - 一致性：和同目录其它代码的风格、命名、错误处理方式是否一致
   - 测试：新增行为有没有测试；原有测试是否仍覆盖修改后的代码
   - 安全：有没有把密钥、token、个人信息写进代码或日志；命令拼接有没有注入空间
   - 副作用：公开接口、配置文件格式、持久化数据结构有没有变（会影响已有用户）
4. **验证而不是猜**：能跑就跑（\`cargo test\`、\`cargo clippy\`、项目自己的脚本）；
   跑不了就在结论里写明"未验证"。
5. **按严重程度排序汇报**：先列会导致错误结果或数据损坏的问题，再列风格与建议；
   每条都给出文件:行号与具体依据，不要泛泛而谈。

## 注意事项

- 不要顺手改代码——审查就是审查，改动等用户点头。
- 不要因为看起来麻烦就跳过 diff 的某一部分；跳过了要说出来。
- 只对看到的内容下结论；推断要标注成推断。

## 自检

- 每条结论都能指到具体文件与行号
- 说了"测试通过"就确实跑过，否则写"未运行测试"
- 没有把风格偏好说成 bug
